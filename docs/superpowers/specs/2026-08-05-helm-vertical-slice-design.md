# HELM — Vertical Slice: Real Login → Real Data → Real AI Output

**Date:** 2026-08-05
**Status:** Approved for planning
**Supersedes:** nothing. Extends `2026-07-30-helm-stage-1-identity-spine-design.md`, which remains valid as written.

## Goal

One thin path through every layer of HELM, working for real. A person signs in with
real credentials, lands in their own tenant, writes a creative brief in Studio, and
receives copy variants generated by a real model provider — persisted, guardrail-
evaluated, tenant-isolated, audited, and billed against a budget ledger.

Breadth is explicitly not the goal. Every other screen stays as it is.

## Why a slice rather than breadth

The platform today is a convincing UI shell over two backends built to conflicting
designs. `helm-app` (Next.js) has fourteen screens and queries Neon directly through
server actions. `helm-api` (FastAPI) is the declared system of record but has only a
health endpoint, four ORM models, and one migration.

Adding features to the shell accumulates work on foundations the Stage 0 contracts say
must not become production. A vertical slice instead proves the intended architecture
end to end at its narrowest point, so every subsequent feature lands on something known
to work.

## Decisions taken

Four questions were open when this design began. All are now settled.

### 1. FastAPI carries the slice

The Stage 1 spec already chose Option B — build FastAPI as the real backend, treat
Phase A as a prototype. That holds. The existing Stage 1 plan is executed as written,
unmodified, as sub-project 1 of four.

The accepted cost is unchanged and worth restating: sub-project 1 rebuilds capability
Phase A already has, and delivers no new user-visible function. The payoff is
sub-projects 2 through 4, which Phase A's architecture could not host.

### 2. Auth0 is the OIDC issuer

This resolves `open-decisions.md` items 1 and 5.

Auth0 was chosen over Keycloak-in-Docker and BFF-minted delegation JWTs because it is
the only option that removes work rather than adding it: standards-compliant OIDC
discovery and JWKS with no container to operate and no signing-key custody while
Vault/KMS remains deferred (`open-decisions.md` #4).

Stage 1's verifier is provider-agnostic by construction — it never learns who the
issuer is. Auth0 therefore enters as four environment values (`OIDC_ISSUER`,
`OIDC_JWKS_URL`, `OIDC_AUDIENCE`, `OIDC_ALLOWED_ALGORITHMS`) and no FastAPI code. If
Auth0 is later replaced, four values change.

### 3. The AI capability is campaign copy generation

Chosen over workspace chat, image generation, and agent runs because it exercises the
entire chain with the least unbuilt machinery. It is text-only, so it needs no token
streaming, no object storage, and no async worker spine. The Studio UI already exists.

### 4. Python version pins are raised to 3.13

The Stage 1 spec flagged this as unresolved. `pyproject.toml` (`requires-python`),
`ruff target-version`, `mypy python_version`, and `.python-version` all declare 3.12;
no 3.12 interpreter is installed and the working venv is 3.13.

Resolution: raise all four declarations to 3.13, matching the machine. No CI enforces
the pin today, so this is a documentation-truth fix rather than a migration.

## Scope decomposition

Four sub-projects, each its own spec → plan → implementation cycle.

| # | Sub-project | Definition of done |
|---|---|---|
| 1 | Identity spine (FastAPI) | `GET /api/v1/tenants` returns real memberships under RLS with an audit event; full security matrix green. **Plan already written.** |
| 2 | Auth0 wiring + first BFF cutover | A real person signs in via Auth0; helm-app renders the tenant list from FastAPI, not Neon. |
| 3 | Model gateway with one real adapter | FastAPI calls a real provider, enforces a per-tenant budget cap, and records usage durably. |
| 4 | Studio generation end-to-end | Brief → generated variants → guardrail verdict → persisted → rendered in the existing Studio UI. |

Sub-project 1 is unchanged from its existing spec and plan. This document specifies 2
through 4.

## Explicitly out of scope

Deferred deliberately, not overlooked:

- **The async spine** (queue, outbox, workers, DLQ). Text generation is served
  synchronously with a timeout. `open-decisions.md` #3 stays open.
- **Image and video generation.** Requires the async spine, R2 object storage, and
  long-running job handling. `open-decisions.md` #10 stays open.
- **LangGraph agent runtime.** `open-decisions.md` #6 stays open.
- **The embedded LLM workspace.** Needs streaming through FastAPI plus conversation
  persistence.
- **Self-serve membership invitation lifecycle.** `open-decisions.md` #8 stays open;
  sub-project 2 provides deliberate seeding only.
- **Vault/KMS.** `open-decisions.md` #4 stays open; provider keys remain in environment
  variables behind a single accessor.
- **Migrating campaigns and approvals off Phase A.** They keep their existing path
  until their FastAPI endpoints exist.
- **The eleven other UI surfaces.** Untouched.

# Sub-project 2 — Auth0 and the first BFF cutover

Two jobs that must land together: make a real human able to sign in, and make helm-app
read one thing from FastAPI instead of Neon.

## Auth0 configuration

One Auth0 account (Auth0 calls this a "tenant"; throughout this document *tenant*
unqualified always means a HELM tenant, never an Auth0 one) containing:

- An **API** with identifier `helm-api`. This becomes `OIDC_AUDIENCE`. Signing algorithm
  RS256, which Stage 1's config validator already requires (it refuses symmetric
  algorithms to close the algorithm-confusion vector).
- A **Regular Web Application** for helm-app, holding the client id and secret Auth.js
  uses.

FastAPI gains no Auth0 SDK, no vendor library, and no Auth0-shaped code. The four
environment values are the entire backend integration.

## helm-app changes

Auth.js already exists and gains an Auth0 provider. The critical detail: the session
must carry the Auth0 **access token**, not the ID token. Only the access token bears the
`aud: helm-api` claim Stage 1's verifier requires; an ID token presented to FastAPI is
correctly rejected as wrong-audience.

A new module `lib/server/helm-api-client.ts` owns every call to FastAPI: base URL,
bearer-token attachment, the `X-HELM-Active-Tenant` hint, request timeout, and
translation of RFC 9457 problem responses into typed errors. It is the only place in
helm-app that knows FastAPI's URL.

## Deliberate user provisioning

Stage 1 refuses to auto-create users: a valid token for an unknown subject raises
`no_membership`. This is correct — implicit provisioning from a token is how tenants
acquire members nobody decided to add — but it means a freshly signed-up human is
locked out.

This sub-project adds an audited CLI command that creates a user with a given
`(identity_issuer, identity_subject)` and grants a membership with a role. It writes an
audit event like any other mutation.

It is not an invitation lifecycle. That is `open-decisions.md` #8 and stays open.

## The cutover

helm-app's tenant switcher stops querying Neon and calls `GET /api/v1/tenants` through
the new client. Only the tenant list moves.

**The seam, stated plainly:** after this sub-project tenant identity comes from FastAPI
while campaign and approval data still come from Neon directly. Two sources of truth,
temporarily. This is the cost of slice-first ordering, and it resolves as later
endpoints migrate. What keeps it safe is that both read the same tenant ids, and Phase
A's boot guard (`assertRuntimeRoleCannotBypassRls`) still refuses to serve tenant-scoped
queries through an RLS-bypassing role.

## Prerequisite repointing

`NEON_DATABASE_URL` currently points at `neondb_owner`, an RLS-bypassing role. The boot
guard correctly refuses to serve tenant-scoped queries through it, which means no real
data renders locally today. `npm run db:provision-app-role` exists; running it and
repointing the variable to `helm_app` is a prerequisite of this sub-project, because a
human cannot see anything real until it happens.

## Testing

Auth0 is never contacted in tests. Stage 1's local RSA keypair and in-memory JWKS stand
in — which is exactly what provider-agnostic design buys.

- A token with the wrong audience is refused.
- A valid token for an unprovisioned subject receives `no_membership`, identical to the
  response for a tenant that does not exist.
- The HTTP client translates a FastAPI problem response into a typed UI error without
  leaking internals, connection strings, or raw provider errors.
- A request with no token never reaches FastAPI.
- The provisioning command creates exactly one user and one membership, and writes an
  audit event.

# Sub-project 3 — The model gateway

This replaces `helm-app/lib/gateway/gateway.ts` — environment-variable routing with no
adapters, no ledger, and no durable usage record — with a real gateway inside FastAPI.

Per `open-decisions.md` #9 the gateway "starts in-process as an internal FastAPI module
with an extraction-ready boundary". It is a module, not a service, but its seams are
drawn as though it will one day be lifted out.

## Modules

| Module | Purpose | Depends on |
|---|---|---|
| `gateway/contracts.py` | Provider-neutral request, response, and usage types. Pure, no I/O. | nothing |
| `gateway/adapters/anthropic.py` | Translates contract → provider SDK → contract. The only file that names a vendor. | contracts |
| `gateway/ledger.py` | Budget reservation, spend recording, cap enforcement. | contracts, repositories |
| `gateway/service.py` | Composes: resolve policy → reserve → call adapter → record usage. | all of the above |
| `gateway/keys.py` | Single accessor for provider credentials. | config |

`contracts.py` being provider-neutral *is* the extraction-ready boundary. A second
adapter is a new file, never a change to the service.

`keys.py` exists so that provider credentials are read in one place rather than through
`os.environ` scattered across adapters. Vault/KMS is deferred (`open-decisions.md` #4);
when it arrives it replaces one module.

## The budget ledger

The naive design — record spend after a successful call — is wrong under concurrency:
unbounded simultaneous requests all pass the cap check before any of them records.

**Reserve before, reconcile after.** The cap check and a reservation row are written in
one transaction. The provider call then happens. Actual usage reconciles the
reservation. A crash mid-call leaves a reservation that a sweep expires.

This is deliberately pessimistic: the failure mode is refusing spend you could have
afforded, never spending money you did not have.

Caps are per-tenant, stored per-tenant, and enforced under RLS like every other
tenant-owned row. Exceeding one returns a distinct problem code — `budget_exceeded`,
HTTP 402 — because a marketer must be told they are out of budget rather than shown a
generic failure.

## Model policy

`open-decisions.md` #9 (approved models, allowed data classes per provider, regional
processing, fallback behaviour) is **not resolved here**. It is made configurable and
auditable instead: a policy table mapping task kind → model id → provider, with an
allowed-data-class field that starts permissive and tightens when compliance rules.

The slice uses one entry: copy generation → Claude.

**Provider fallback is deliberately absent.** A failed provider call returns an error
rather than silently retrying against a different vendor. Silent cross-provider fallback
is precisely the behaviour a data-residency decision must govern, and implementing it
before that decision exists would create an undocumented data path.

## Durable usage and audit

The risk log flags the current gateway for having "no durable usage/audit transaction."
Every call writes a usage row — tenant, model, provider, tokens in and out, cost,
latency, outcome — committed together with the reservation reconciliation.

This also gives the existing Gateway screen real numbers to render later at near-zero
additional cost.

## Testing

- Adapters run against recorded fixtures. No test spends money or requires network.
- One opt-in smoke test calls the real provider when an API key is present and skips
  cleanly otherwise, matching how the existing testcontainer tests skip without Docker.
- **The ledger concurrency test:** N simultaneous requests against a cap permitting
  fewer than N must result in exactly the permitted number succeeding. This is the test
  the naive design fails.
- Cap enforcement is tenant-scoped: one tenant exhausting its budget does not affect
  another.
- A provider error produces a problem response that never echoes raw provider output.

# Sub-project 4 — Studio generation end-to-end

Studio today is 87 lines of client-side mock: `generate()` fabricates variants, the SEBI
gate is decorative, nothing persists. This makes it real and closes the slice.

## Request path

```
Studio brief (helm-app)
  → POST /api/v1/creative/generations   [Bearer token, Idempotency-Key]
  → verify JWT → resolve user → resolve membership → effective scopes
  → require creative:write
  → open transaction, SET LOCAL app.tenant_id
  → replay check against idempotency_keys
  → gateway.generate(brief, policy=copy_generation)
  → guardrail evaluation → verdict per variant
  → persist generation + variants + verdicts, append audit event
  → commit
  → render variants with their verdicts
```

The `creative:write` scope this endpoint requires already exists: Stage 1 defines it in
`app/auth/scopes.py`, grants it to the `creative` and `owner` roles, and caps
`client_viewer` below it. No scope work is needed here.

**Timeout behaviour.** Serving generation synchronously is only safe with a bound. The
gateway applies a request timeout; exceeding it aborts the provider call, releases the
budget reservation, and returns a problem response. No partial generation is persisted.
If real-world latency makes the bound routinely unreachable, that is the signal that
this capability needs the deferred async spine — a deliberate trigger, not a surprise.

Two elements earn their place. The **idempotency key** — whose table Stage 1 already
creates — means a double-click or a network retry does not bill twice; the second
request replays the stored response. The **audit event** commits with the variants or
not at all, the atomicity property Stage 1's test matrix already proves.

## Data model

One Alembic migration adding two tenant-owned tables. Both follow the pattern every
existing table follows: `tenant_id` foreign key, RLS enabled **and** forced, isolation
policy via `helm_tenant_id()`.

- **`creative_generations`** — the brief, resolved model and provider, status, and
  linkage to the gateway usage row.
- **`creative_variants`** — each variant's text, guardrail verdict, flag reason,
  acknowledgement state, and shipped state.

Variants are rows rather than a JSON blob because Ship and Acknowledge transition
individual variant state, and per-row state transitions belong in per-row records.

## The guardrail boundary, and its honest limit

`open-decisions.md` is blunt: "Regex-only PII/injection/compliance checks are
insufficient for DPDP/SEBI requirements and **must not be represented as production
assurance**."

The design is therefore a real, extensible evaluation boundary — a `guardrails/` module
with a rule interface, evaluating each variant to `pass` or `flag` with a reason —
seeded with the deterministic SEBI-adjacent checks the mockup implies: unsubstantiated
return claims, missing risk disclosure, guarantee language. It is a genuine checkpoint
with a real interface that an LLM-based or vendor evaluator plugs into later.

**It is not compliance assurance, and the UI must not imply that it is.** The existing
Studio badge reads "SEBI pass", which overclaims. It becomes "Checks passed", with the
limitation stated on the surface. This is not pedantry: representing regex checks as
SEBI compliance to a financial-services client is a real liability.

## Studio UI changes

Minimal, and mostly deletion. `generate()` stops fabricating variants and calls a server
action. Variants render from the response. `ship` and `acknowledge` become persisted,
audited transitions rather than `useState` mutations.

This closes fast-follow item 2 (acknowledge-to-ship, previously deferred) for free,
because acknowledgement is now a real audited state change rather than local component
state.

## Testing

**Unit.** Guardrail rules against known-flagging and known-passing copy, including the
boundary cases where a rule nearly fires.

**Integration, on testcontainers.** Cross-tenant read denial on both new tables. A
`creative` role can generate; a `client_viewer` receives `insufficient_scope`. The same
idempotency key submitted twice produces one generation and one ledger charge. A
flagged variant cannot be shipped without a recorded acknowledgement.

**API.** The full chain with a forged token, a valid token lacking `creative:write`, and
a valid scoped token.

## Definition of done for the whole slice

A real person signs in through Auth0, lands in their tenant, writes a brief in Studio,
and sees copy variants generated by Claude — persisted, guardrail-evaluated,
tenant-isolated, audited, and billed against a real budget ledger.

Gates, all green:

- FastAPI: `pytest`, `ruff check`, `mypy --strict`
- helm-app: `vitest`, `eslint`, `tsc --noEmit`

## What this slice leaves for later

Stated so the remaining distance is not a surprise:

- Campaigns and approvals still read Neon directly; their FastAPI endpoints and cutover
  remain.
- Eleven UI surfaces still render mock data.
- The async spine, image generation, agent runtime, and LLM workspace are unbuilt.
- `open-decisions.md` items 2, 3, 4, 6, 7, 8, 9, and 10 remain open. Items 1 and 5 are
  closed by this design.

What the slice buys is that none of that work is speculative any more. Auth, tenancy,
scoping, audit, the gateway, and the guardrail boundary will exist and be proven, so
each remaining feature extends known-working machinery instead of testing an unproven
architecture.
